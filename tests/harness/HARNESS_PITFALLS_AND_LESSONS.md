## 一、本次系统级深度排查挖掘的 8 大高危踩坑反模式

### 踩坑 1：【伪鉴权降级反模式】（假离线演示放行）
- **现象描述**：用户输入任何错误密码或乱码账号，系统均能提示“登录成功”并直接进入业务工作台。
- **根因分析**：
  前端在 `userStore.ts` 的 `login()` 中调用后端 `/auth/login`。后端正常抛出 400 密码错误，前端用 `catch` 捕获后，错误地设计了所谓“离线演示高韧性降级”，直接从预设人员库中默认取出管理员账号，伪造 Token 并强制令 `isLoggedIn = true`。
- **防退化军规**：
  **严禁在正式登录提交逻辑中设置无感知免密降级！** 密码比对失败必须坚决中断并向用户抛出明确的凭证错误提示。快捷体验只能通过显式的“演示账号一键体验”专用通道触发。

### 踩坑 2：【Tab 切换事件断漏与静默 No Data】
- **现象描述**：管理员查看【全院/分仓实时库存】，页面永久呈现 `No Data, Total 0`，而后端数据库中真实存在 15 个批次、1822 件物资。
- **根因分析**：
  前端在 `handleTabChange(tabName)` 中使用了 `if...else if`，唯独漏掉了 `tabName === 'inventory'` 的独立分支，导致掉入默认方法 `fetchOrders()`，从未向后端发起 `fetchRealtimeStock()` 请求；同时路由参数监听 `watch(() => route.query.tab)` 也未声明该分支。
- **防退化军规**：
  凡涉及多选项卡（`el-tab-pane`）与路由 `query.tab` 同步的视图，必须建立映射字典（`TabKey -> FetchHandler`）进行全覆盖分发，严禁使用模糊的 `else` 兜底导致核心选项卡沦为静默死区。

### 3. 【病区切换局部刷新与数据串岗污染】
- **现象描述**：在临床二级库房中从“骨科病区二级库”切换至“心内科病区二级库”，接收入库表格中依然显示骨科的分发调拨单，造成跨科室数据混淆。
- **根因分析**：
  `switchDept(deptCode)` 内部只刷新了申领记录与发料记录，漏掉了接收入库单（`fetchPendingReceives`）与在库台账（`fetchSecondaryInventory`），导致上一个科室的响应式数据未被清理或覆盖。
- **防退化军规**：
  科室/仓库上下文切换属于最高等级的作用域变更。切换时必须清空全局表格数据源，并全量联动重新拉取当前科室下的所有 Tab 数据；后端查询接口必须强制绑定当前科室编码，杜绝非授权科室数据透出。

### 4. 【单向扣库与断头业务流】（缺失接收方双向审核）
- **现象描述**：主库审批请领后，库存未扣减；跨病区调拨开单后单向直接扣库结案，调入目标科室没有任何审核接收与查验确认。
- **根因分析**：
  后端接口仅更新了单据状态，未在数据库原子事务内操作库存；调拨业务直接调用 `to_inv.current_qty += qty`，跳过了实物在途状态（`IN_TRANSFER`）与目标科室验收状态机。
- **防退化军规**：
  医疗物资在科室间的所有物理流转，必须严格遵循“申请/出库方在途预占 -> 接收方实物查验 -> 接收方确认入库增库 / 差异拒收逆向退库”的**双向对账状态机**；审批出库与库存扣减必须在同一个数据库会话事务内完成，不可扣成负数。

### 5. 【流水单号允许手动录入与篡改】
- **现象描述**：跨病区科室调拨弹窗中，调拨单号输入框为空白，允许用户随意手工填写。
- **根因分析**：
  弹窗触发事件直接将 `modalVisible = true`，未调用初始化方法生成单据流水号；表单控件未配置 `disabled` 或 `readonly`。
- **防退化军规**：
  所有医院单据号（`TR...` / `CK...` / `DIST...` / `RK...`）必须由系统按“业务前缀 + 年月日时分秒毫秒 + 随机序列”自动生成，输入框必须强制只读，严禁允许用户手工修改单号。

### 6. 【高值专仓与普通主库功能割裂】
- **现象描述**：普通耗材主库具备全院实时库存穿透与期初建账，而高值专仓仅有局部智能柜列表，管理员无法在同一粒度下穿透查看全院高值物资分布。
- **根因分析**：
  高值专仓视图与普通耗材视图各自独立开发，未遵循统一的仓储中枢规范。
- **防退化军规**：
  高值专仓必须对齐普通主库标准，建立【全院/分仓高值实时在库台账】与【高值专柜期初建账穿透】，支持按院区、主科室、临床科室专柜下钻查看一物一码单品在库状态与效期。

### 7. 【路由导航守卫缺少角色鉴权白名单】
- **现象描述**：非系统管理员通过浏览器地址栏直接输入 `/users`（人员管理）即可绕过侧边栏进入页面。
- **根因分析**：
  前端全局守卫仅判定了登录状态，未对路由元数据 `meta.roles` 进行匹配校验。
- **防退化军规**：
  全局路由守卫必须实施 RBAC 强校验，不具备岗位权限的路由直接重定向至所属工作台并友好提示，杜绝越权违规。

### 8. 【扫码枪回车交互与表单输入脱节】
- **现象描述**：临床使用扫码枪扫码录入 UDI 或批号后，光标停留在输入框，必须手动放下扫码枪再去点鼠标点击“查询”或“验码”。
- **根因分析**：
  所有扫码枪硬件在扫码完成时均会自动追加发送 `Enter`（ASCII 13）信号。前端输入框未监听 `@keyup.enter` 事件。
- **防退化军规**：
  所有涉及物料编码、批号、UDI 码、单据号检索的输入框，必须统一监听 `@keyup.enter`，实现扫码即刻触发查询或验码，极大提升临床作业流转效率。

### 9. 【Vue3 `<script setup>` 中 `watch` 带 `immediate: true` 引发暂时性死区 (TDZ)】
- **现象描述**：页面初次加载时控制台报 `PageError: Cannot access 'le' (或某函数) before initialization`，导致页面脚本中断。
- **根因分析**：
  在 `<script setup>` 顶层使用 `watch(..., { immediate: true })`，如果该回调内部调用了在代码下方才定义的 `function` 或 `const` 异步拉取函数，构建工具将其转换并打包后，会因为在声明赋值前同步执行而触发 JavaScript 暂时性死区（Temporal Dead Zone）。
- **防退化军规**：
  - 严禁在 fetch 数据函数定义之前声明带 `immediate: true` 的 `watch`；
  - 推荐不在 `watch` 中开启 `immediate: true`，页面初次加载统一由 `onMounted` 钩子按需调度，`watch` 仅用于监听路由或状态的后续增量变化。

### 10. 【Windows 路径带空格导致 Chromium `--user-data-dir` 启动崩溃】
- **现象描述**：Playwright 启动持久化上下文时崩溃，提示 `Target page, context or browser has been closed`。
- **根因分析**：
  当 Windows 系统的 `os.tmpdir()` 包含空格（例如 `E:\TEMP and TMP\TEMP`）时，Chromium 命令行参数 `--user-data-dir=...` 会被误切分为多个参数导致解析异常崩溃。
- **防退化军规**：
  在持久化浏览器配置中，临时 Profile 路径必须采用明确且绝对无空格的路径（如 `C:/Users/.../AppData/Local/Temp_pw/...`），彻底杜绝跨机器路径空格异常。

## 二、Harness 自动化回环测试防退化拦截标准

在执行任何提交或上线前，必须通过 `tests/harness/runner.js` 与 Playwright 端到端脚本进行以下强制断言拦截：
1. **密码错误阻断断言**：模拟错误密码提交，断言页面停留在登录页并弹出错误提示，严禁放行跳转；
2. **全院实时在库批次断言**：进入【全院/分仓实时库存】，断言批次总数 > 0，金额合法格式化；
3. **主库审批原子扣库断言**：审批单据前后，断言主库在库数量精确减少，二级库待接收列表精确增加；
4. **科室切换数据隔离断言**：骨科切换为心内科后，断言骨科单据从当前表格中完全消失，只呈现心内科数据；
5. **调拨单号全自动生成断言**：打开调拨弹窗，断言单号以 `TR936` 开头且 `readonly=true`；
6. **调拨双向审核断言**：调出提交后为待接收状态，目标科室审核通过后目标科室在库增加，结案归档。
